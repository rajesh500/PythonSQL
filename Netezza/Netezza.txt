Question:
For a 10 TB Netezza-to-Azure Databricks migration, use a phased migration with ADF + Self-hosted Integration Runtime + ADLS Gen2 + Databricks.

Netezza 10 TB --> ADF + SHIR --> ADLS landing --> Bronze Delta --> Silver Delta --> Gold --> Reporting BI

Do not treat the 10 TB database as one copy operation. Divide it by table and split large tables into restartable extraction chunks.

7. Divide large tables into chunks
Do not run:

SELECT *
FROM sales;

for a 5 TB table in one copy operation. A failure near the end would make recovery difficult.

Date-range extraction

Suppose SALES contains five years of data:

-- Chunk 1
SELECT *
FROM sales
WHERE sale_date >= DATE '2021-01-01'
  AND sale_date <  DATE '2021-02-01';

-- Chunk 2
SELECT *
FROM sales
WHERE sale_date >= DATE '2021-02-01'
  AND sale_date <  DATE '2021-03-01';

Notice the boundary pattern:

column >= lower_bound
AND column < upper_bound

This prevents overlaps and gaps.

Numeric-range extraction
SELECT *
FROM orders
WHERE order_id >= 1
  AND order_id < 10000000;

Next chunk:

SELECT *
FROM orders
WHERE order_id >= 10000000
  AND order_id < 20000000;
Choosing a split column

A good split column should be:

Indexed logically through Netezza organization/zone-map behavior
Well distributed
Non-null, or have a separate null-data extraction
Stable during the migration
Suitable for non-overlapping ranges

Possible columns:

Transaction date
Created timestamp
Increasing ID
Batch ID
Fiscal year/month

Avoid:

Highly skewed columns
Frequently updated split values
Low-cardinality columns such as status
Nullable columns without separate handling

For nullable keys, add a separate chunk:

SELECT *
FROM sales
WHERE partition_column IS NULL;


8. Control parallelism
Run multiple table/chunk extractions concurrently, but do not overload Netezza.

For example, begin with:

4 concurrent extractions
Monitor Netezza CPU, disk and query queues
Monitor SHIR CPU, memory and network
Increase to 8 if the environment remains stable
Reduce concurrency during business hours
Run the largest extraction window during off-peak hours

Do not start with arbitrary high concurrency such as 50. Netezza is also serving production queries, and excessive extraction can cause:

Resource contention
Query queuing
Increased disk scanning
Network saturation
Production SLA impact

Test several configurations and measure actual throughput.


9. Estimate migration duration
Theoretical network-transfer time is:

$$ \text{Time}= \frac{\text{Data size in bits}} {\text{Network throughput in bits per second}} $$

Approximate theoretical times for 10 TB:

Available bandwidth Theoretical minimum More practical planning range
100 Mbps    About 9.3 days  12–20 days
500 Mbps    About 1.9 days  3–5 days
1 Gbps  About 22 hours  1.5–3 days
10 Gbps About 2.2 hours Usually limited by source, SHIR or storage

Practical time is longer because of:

Netezza query and export speed
Network utilization
Compression
SHIR capacity
File creation
Azure Storage throughput
Retries
Validation
Production throttling

Run a representative test:

Select a 100–500 GB table.
Copy it using expected production settings.
Measure end-to-end throughput.
Repeat during peak and off-peak periods.
Extrapolate conservatively.

Example:

500 GB test completed in 3 hours
Average throughput = 166.7 GB/hour

10,000 GB ÷ 166.7 = approximately 60 hours
Add 30% contingency = approximately 78 hours

This is more reliable than estimating from the internet circuit alone.


10. Decide whether Data Box is needed
For a 10 TB database, network transfer through ADF is normally more practical if adequate bandwidth is available.

Data Box is generally positioned for larger transfers, particularly above approximately 40 TB or where network connectivity is severely limited. Azure Data Box overview

Use Data Box for 10 TB only when:

Bandwidth is extremely limited
Security policy requires offline movement
Network transfer would take too long
Production cannot tolerate continuous extraction traffic

Data Box still requires:

Exporting Netezza tables into files.
Copying the files to Data Box.
Shipping the device.
Uploading the data into ADLS.
Loading ADLS files into Databricks.

It does not extract directly from Netezza.


11. Load the landing files into Bronze Delta
Example:

from pyspark.sql.functions import current_timestamp, input_file_name

source_path = (
    "abfss://landing@account.dfs.core.windows.net/"
    "netezza/SALESDB/PUBLIC/SALES/"
)

sales_df = (
    spark.read
         .format("parquet")
         .load(source_path)
         .withColumn("_ingestion_timestamp", current_timestamp())
         .withColumn("_source_file", input_file_name())
)

(
    sales_df.write
            .format("delta")
            .mode("append")
            .partitionBy("sale_year")
            .saveAsTable("bronze.sales")
)

Be careful with physical partitioning. Do not partition by:

Customer ID
Transaction ID
High-cardinality timestamp
Columns that create thousands of small directories

Consider Delta Lake Liquid Clustering for large tables that have changing or multiple filter patterns.

14. Implement incremental loading
Before starting the historical extraction, record a consistent cutoff value.

For example:

SELECT MAX(updated_timestamp)
FROM sales;

Assume the initial cutoff is:

2026-09-01 00:00:00

Historical extraction:

SELECT *
FROM sales
WHERE updated_timestamp <= TIMESTAMP '2026-09-01 00:00:00';

Incremental extraction:

SELECT *
FROM sales
WHERE updated_timestamp >  :old_watermark
  AND updated_timestamp <= :new_watermark;

Use this boundary consistently:

> old watermark
<= new watermark

Only advance the stored watermark after:

Extraction succeeds
Bronze load succeeds
Validation succeeds
Target commit succeeds

For inserts and updates, use Delta MERGE:

MERGE INTO silver.sales AS target
USING bronze.sales_increment AS source
ON target.sale_id = source.sale_id

WHEN MATCHED AND source.updated_timestamp > target.updated_timestamp
THEN UPDATE SET *

WHEN NOT MATCHED
THEN INSERT *;

For source deletes, determine whether Netezza provides:

A delete indicator
Soft-delete status
Audit table
CDC/change table
Periodic key comparison

An updated timestamp alone cannot detect hard deletes.

18. Execute cutover
A practical cutover sequence is:

Complete all historical chunks.
Reconcile the historical load.
Run incremental loads regularly.
Complete user acceptance testing.
Freeze Netezza ETL or establish a final cutoff.
Record the final high watermark.
Run the final incremental load.
Reconcile critical tables and reports.
Redirect applications and BI tools.
Monitor Databricks workloads.
Retain Netezza temporarily for rollback.
Decommission only after business approval.

Define rollback criteria before cutover:

Critical reconciliation failure
Unacceptable performance
Missing source changes
Application connectivity failure
Security or permission failure
SLA breach
Recommended approach for your 10 TB case

A reasonable starting design would be:

Use ADF with Self-hosted IR.
Land data in ADLS as compressed Parquet.
Migrate small tables in full.
Split large tables by month, date or numeric range.
Begin with 4 concurrent extractions and tune through testing.
Use a 100–500 GB performance test to determine actual throughput.
Load landing files into Bronze Delta.
Convert and validate Silver/Gold transformations separately.
Capture incremental changes with watermarks.
Use Delta MERGE for inserts and updates.
Maintain chunk-level status for restartability.
Use Data Box only if network testing shows an unacceptable migration duration.
