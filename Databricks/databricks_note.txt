Z-ordering:
let say you have multiple partitions and you have country code in those partitions.
partition1  IN, USA, AUS
partition2  AUS, IN, IN 
partition3  USA, IN, USA
if you try to filter out the data on country bases then all the partitions need to be scanned and filter it out.

If we use zordering then in the back it will re-partition the on country bases, it will go that particular partition and fetch the data.
partition1  USA, USA, USA
partition2  IN, IN, IN 
partition3  AUS, AUS, AUS.

zordering will do the re-ordering and store in the metadata not in the original location.
Z-ordering must be run after the table load because it is a maintenance operation that reorganizes data that already exists on disk.

Partitioning is also doing the same thing then what z-ordering is doing here.
Example:
Suppose sales is partitioned by sale_date:

(
    df.write
      .format("delta")
      .partitionBy("sale_date")
      .mode("append")
      .saveAsTable("sales")
)

Storage:

sales/
├── sale_date=2026-09-01/
│   ├── file1.parquet
│   ├── file2.parquet
│   └── file3.parquet
├── sale_date=2026-09-02/
│   ├── file1.parquet
│   ├── file2.parquet
│   └── file3.parquet
Query 1: Filter only by partition column
SELECT *
FROM sales
WHERE sale_date = DATE '2026-09-01';

Partition pruning skips all other dates.

If the selected partition contains only a small amount of data, partitioning may be sufficient. You may not need Z-Ordering.

Query 2: Filter by partition and customer
SELECT *
FROM sales
WHERE sale_date = DATE '2026-09-01'
  AND customer_id = 1001;

Partition pruning selects:

sale_date=2026-09-01

But that partition might contain 100 files. If customer_id=1001 is scattered across many files, Databricks may need to inspect many of them.

Z-Ordering can organize customer IDs inside each partition:

OPTIMIZE sales
WHERE sale_date >= DATE '2026-08-01'
ZORDER BY (customer_id);

Then Delta statistics can skip files whose customer range does not contain 1001.


Do not Z-Order by the partition column:

Usually this is redundant:

PARTITIONED BY (sale_date);

OPTIMIZE sales
ZORDER BY (sale_date);

Rows inside each partition already have the same sale_date. Z-Ordering on that same column provides little or no additional benefit.

Liquid Clustering:
Liquid Clustering is a modern data layout optimization feature in Delta Lake that replaces many traditional uses of partitioning and Z-Ordering. 
It allows Delta tables to continuously reorganize data based on clustering keys without requiring static partitions.

Why was Liquid Clustering introduced?

Traditional partitioning has limitations:

Too many partitions → millions of small files.
Too few partitions → poor query performance.
Changing partition columns later is difficult.
Frequent updates can lead to data skew.



Liquid Clustering + optimize using both this reorganize of data will be done.

Z-Ordering is a one-time optimization technique.

File2

500


Limitation

Tomorrow another 100 GB arrives.

The new files are not automatically Z-Ordered.


Every new data got loaded into the table z-ordering need to be run to reorganize the data.

Liquid Clustering is a persistent table property that defines how data should be organized over time.
Continuously organize data.
No need to rerun it to reorganize the data.

## Delta lake:
Delta lake was built on top of data lake storage.
delta lake is an open storage framework that brings reliability and performance to data lakes.
key features
1. schema enforcement rejects writes to a table if the incoming data structure does not match the existing table schema.
2. time travel / versioning – history
3. update
4. delete
5. merge scd-1 
6. ACID transactions
7. schema evolution : automatically adjust its structure.
8. performance optimizations such as OPTIMIZE, Z-ordering..
In my databricks projects, i use delta lake for incremental processing, CDC implementations, and maintaining reliable Bronze, Silver and 
Gold layers in a medallion architecture.

Example:
schema enforcement:
Schema enforcement validates incoming data against the Delta table schema and rejects incompatible writes, protecting data quality.

Suppose the target Delta table has:

customer_id  BIGINT
name         STRING
email        STRING

Incoming data has:

customer_id  BIGINT
name         STRING
phone        STRING

A normal append can fail because phone is not part of the target schema:

incoming_df.write \
    .format("delta") \
    .mode("append") \
    .saveAsTable("prod.silver.customers")

This is schema enforcement. Delta validates the write before accepting the data, protecting the table from accidental schema changes.

## Shuffle:
What is Shuffling in Spark?

Shuffling is the process of moving data across executors/partitions so that Spark can perform operations such as joins, aggregations, sorting, and distinct.

It is one of the most expensive operations in Spark because it involves:

Network I/O
Disk I/O
Serialization/Deserialization
Sorting


Simple Example

Suppose you have data:

Partition 1                Partition 2

(A,100)                    (A,200)
(B,300)                    (B,400)
(C,500)                    (C,600)

Now run:

df.groupBy("customer_id").sum("amount")

Spark needs all records for the same customer together.


After shuffle:
Partition 1
A,100
A,200

Partition 2
B,300
B,400

Partition 3
C,500
C,600

Spark moved data across executors. This movement is called shuffle.


Operations That Cause Shuffle:
df.groupBy("customer_id").sum()
df1.join(df2, "customer_id")
df.distinct()
df.dropDuplicates()
5. orderBy / sort
df.orderBy("amount")
df.repartition(100)

but this can achieve using autoloader.
source path:
target path:
checkpoint locator path:

During the writing, mention this checkpoint locator path, this auto loader  will handle checkpoint incase of failure.
during this process as well split the large file into multiple files.


from pyspark.sql.functions import current_timestamp, input_file_name

source_path = "abfss://apexusdev@apexusdev.dfs.core.windows.net/input/parquet/"
target_path = "abfss://apexusdev@apexusdev.dfs.core.windows.net/delta/customer/"
checkpoint_path = "abfss://apexusdev@apexusdev.dfs.core.windows.net/checkpoints/customer/"

df = spark.readStream \
    .format("cloudFiles") \
    .option("cloudFiles.format", "parquet") \
    .load(source_path)

final_df = df.withColumn("source_file", input_file_name()) \
             .withColumn("processed_time", current_timestamp())

query = final_df.writeStream \
    .format("delta") \
    .option("checkpointLocation", checkpoint_path) \
    .option("mergeSchema", "true") \
    .outputMode("append") \
    .trigger(availableNow=True) \
    .start(target_path)

query.awaitTermination()

CDF: (Change Data Feed): 
CDF (Change Data Feed) in Databricks Delta Lake is a feature that records row-level changes (inserts, updates, and deletes) made to a Delta table. 
Instead of reading the entire table every time, downstream processes can read only the changes since a specific version or timestamp.

This is a property in the delta table, need to be enable it during creating a table or after creating the table.
CREATE TABLE customers (
    customer_id INT,
    name STRING,
    city STRING
)
USING DELTA
TBLPROPERTIES (
    delta.enableChangeDataFeed = true
);


or Alter table customer set TBLPROPERTIES (
    delta.enableChangeDataFeed = true
);


Ex: customer is table:
today data got inserted it will store in specific version1
next day some inserted, deleted, and update it will store in specific version2
Now query this table after version1 what all the changes happended on version2 this can be tracked using some specific metadata columns.

_change_type    (insert, update, delete)
_commit_version (v1, v2, v3)
_commit_timestamp
update_preimage   before update 
update_postimage  after update


SELECT *
FROM table_changes('silver_customers', 1);

SELECT *
FROM table_changes('silver_customers', 2);


Every time querying this table need to know pervious what version we queried or pulled in order to know that 
create a control table and store the pulled version and update to next version.


CREATE TABLE cdf_control (
    table_name STRING,
    last_processed_version BIGINT
);


In the backend how data is pulled for CDF is
same as delta transaction log created for every transaction.
for every update and delete cdf file is also get created.

In the delta transaction log file we have a cdc info as 
{"cdc":{"path":"_change_data/cdc-00002.parquet"}}  what operation is done for CDF.

When table_changes(table, 1, 3) is queried, first it read all the delta transaction log files
00000000000000000001.json
00000000000000000002.json
00000000000000000003.json
from their. it will know what cdf changes are happened in between these three versions.
for insert it will read parquet files of that version, for update and delete it reads from cdf files for version 1 to 3.


Example:
if there are three delta transaction log file from which file it reads data.
It depends on the version range passed to table_changes(). Databricks reads the Delta-log commits in that range and then reads the data/CDF files referenced by those commits.

Assume the table has:

_delta_log/
├── 00000000000000000000.json   ← Create table
├── 00000000000000000001.json   ← Insert
├── 00000000000000000002.json   ← Update
└── 00000000000000000003.json   ← Delete

There are two different types of checkpoints in Delta Lake, and they are often confused in interviews.

Delta Log Checkpoints (automatic, for transaction log performance)
Structured Streaming Checkpoints (for stream recovery)

Since you asked about Delta Lake table with checkpoint implementation, I'll explain Delta Log Checkpoints.


What is a Delta Log Checkpoint?

Every transaction on a Delta table creates a JSON log file in _delta_log.

Example:

sales/
│
├── part-00001.parquet
├── part-00002.parquet
│
└── _delta_log/
      00000000000000000000.json
      00000000000000000001.json
      00000000000000000002.json
      ...

Suppose your ETL runs every 5 minutes.

One day later:
288 commits/day
After a month:
8640 JSON files
If a new Spark cluster wants to read the table, it would have to read thousands of JSON transaction logs.
That would be slow.
Solution: Checkpoint

Delta automatically creates a checkpoint after a configurable number of commits (by default, every 10 commits).

Example:
_delta_log/
00000000000000000000.json
00000000000000000001.json
...
00000000000000000009.json

00000000000000000010.checkpoint.parquet

Instead of replaying all 10 JSON files, Spark reads:
Checkpoint
      +
Remaining JSON files

This makes table loading much faster.

Interview Answer

A Delta Log checkpoint is a Parquet snapshot of a Delta table's transaction log. Every write operation creates a JSON log in the _delta_log directory, and replaying thousands of JSON files would slow table initialization. To avoid this, Delta Lake automatically creates checkpoint Parquet files at regular commit intervals (default every 10 commits). When a table is read, Spark loads the latest checkpoint and only the newer JSON logs, significantly reducing metadata read time and improving query performance.

In this scenario, you don't write any checkpoint code—Delta Lake manages transaction log checkpoints automatically in the background.

Pipeline failed halfway:
If we are writing data into delta table, halfway pipeline failure data shouldn't get commited into delta table,
because delta supports ACID properties. If any DB support ACID properties data load should get sucessful or fail.
If half data write and fail at halfway then these half data reverted back.

Let’s say I am processing 10,000 records and writing them to a Delta table. 
The pipeline fails after approximately 5,000 records have been written.
Spark may have successfully created three Parquet data files, and those files may be physically visible 
in the target storage location. While writing the fourth Parquet file, the pipeline fails, so that file may be 
incomplete or corrupted.
However, the three completed Parquet files were only staged; they were not committed individually. 
Because the overall Delta write failed, no new transaction was committed to the _delta_log.
Since the Delta transaction log does not reference any of these newly created Parquet files,
 none of the 5,000 records are visible when querying the Delta table. Readers continue to see the previous 
 successfully committed table version.
Therefore, even though some Parquet files may physically exist in storage, the entire Delta write is treated 
as failed. The unreferenced Parquet files are orphan files and can later be removed by VACUUM, subject to the 
configured retention period.

## why small file problem is an issue:
Suppose you have 1 TB of data:
Option A: 1,024 files × 1 GB
Option B: 1,000,000 files × approximately 1 MB

Both contain roughly the same data, but Option B is significantly slower.

1. File-listing overhead
Before processing, the Spark driver must discover and collect metadata about the files:
List file
Read path
Read size
Read partition information
Plan input tasks

Listing hundreds of thousands of files in ADLS or S3 can make query planning slow and consume driver memory.

2. Storage open/close overhead
Every file requires operations such as:
Open connection → Read metadata/footer → Read data → Close connection
For a 1 MB file, Spark may spend more time opening and closing it than reading its contents.

3. Excessive task-scheduling overhead.
    1 partition = 1 task
the execution of task,  driver must manage every task:

Create the task.
Serialize task information.
Send it to an executor.
Track its execution.
Receive status and metrics.
Handle failures and retries.
Mark it completed.

That work is task-scheduling overhead.

This create long job planning time.
Slow stage startup.
Long job-planning time.
Large driver memory usage.
Short executor tasks.
Idle gaps between tasks.
Large Spark event logs.
Slow Spark UI rendering.
Increased retry-management overhead.

4. Parquet footer overhead
Every Parquet file has its own footer containing schema and metadata:
file_001.parquet → footer
file_002.parquet → footer
file_003.parquet → footer

Spark may need to read metadata from many separate files before or during processing.

5. Poor cluster utilization
Executors repeatedly open small files and complete tiny tasks instead of spending most of their time processing data.
A Spark UI symptom could look like:
Number of tasks: 100,000
Task duration:    100–500 milliseconds
Actual compute:   very low
Scheduling time:  very high

Finally, poor performance and some time pipeline can be failed.

CREATE OR REPLACE FUNCTION production.sales.region_filter(row_region STRING)
RETURNS BOOLEAN
RETURN
    current_user() = 'rajeshjkv5@gmail.com' OR

ABAC: Attribute based access control.
Attribute means field, it means field based access control.

ABAC means Attribute-Based Access Control. In Databricks Unity Catalog, 
it uses governed tags and centralized policies to automatically apply row filters, column masks,
 and supported privilege policies across tables.

Here we can create function, policy and governed tag.
function and policy created one time but just tag need to attached new table.

tags:  at column level 
ALTER TABLE prod.sales.orders
SET TAGS ('security_scope' = 'regional');

ALTER TABLE prod.sales.orders
ALTER COLUMN region
SET TAGS ('data_attribute' = 'region');

governed tags:
CREATE GOVERNED TAG security_scope VALUES ('regional');
CREATE GOVERNED TAG data_attribute VALUES ('region');

These two are one time creation for each activity.
activity means, masking, region-based access....
