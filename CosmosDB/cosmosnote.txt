When you create an Azure Cosmos DB account using the Core API (also widely known as the NoSQL API or SQL API), 
you are creating a fully managed, cloud-native NoSQL document database.

Here is what you need to know about this specific database type:
• Data Format: It stores data natively as JSON documents. This means it is schema-agnostic, 
				allowing you to store flexible, semi-structured data without defining rigid tables and columns beforehand.
• Query Language: Even though it is a NoSQL database, you use a custom, familiar SQL-like syntax to query your JSON documents. 
					This gives developers who already know relational SQL a very smooth learning curve.
• Hierarchy: Within the database account, you create Databases, which act as namespaces. Inside those databases, 
				you create Containers (similar to relational tables) to hold your JSON documents (similar to rows).
• Key Strengths: It offers automatic indexing of all properties, single-digit millisecond response times, and turn-key global replication

Provisioned throughput: 
Provisioned throughput means the processing capacity you reserve for Cosmos DB to handle reads, writes, and queries. It is measured in Request Units per second (RU/s).
- RU: The amount of work an operation consumes.
- RU/s: The amount of work Cosmos DB can handle each second.

Request units:
compute resource allocation for DB queries.

 

• 1 RU is exactly equal to a point read (fetching by ID and partition key) of a 1 KB item.

Hot Partition:
A hot partition in Cosmos DB occurs when one partition receives much more read/write work than others, exhausting its available throughput while others still have capacity.

Example:
Logical partition	Requests per second
C101					5,000
C102					50
C103					30
C104					20

Most requests target C101. This makes C101 a hot logical partition.

Imagine a container with manual provisioned throughput of 12,000 RU/s, distributed across three physical partitions:
Physical partition			Available throughput				Requested workload
P1 — contains C101				4,000 RU/s						6,000 RU/s
P2								4,000 RU/s						500 RU/s
P3								4,000 RU/s						500 RU/s


The total workload is only 7,000 RU/s, below the container’s 12,000 RU/s.
However, P1 needs 6,000 RU/s and has only 4,000 RU/s. It can throttle while P2 and P3 remain underused. A logical partition’s data stays together on one physical partition, so that hot key cannot simply spread across all three.


Resolution:
For example, instead of putting every C101 order under "C101", a redesigned key could distribute orders across buckets:
C101-0
C101-1
C101-2
C101-3

These become separate logical partitions that Cosmos DB can distribute. The tradeoff is that retrieving all C101 orders now requires querying multiple buckets.

If the data is distributed across multiple partition then it works as cross partition.
Cross-partition queries can execute in parallel, so they are not always slower. If the original partition was heavily throttled, spreading the workload may improve response times despite the extra query work.



Time to Live (TTL):
Time to Live (TTL) in Azure Cosmos DB is a built-in feature that automatically deletes items from a container after a designated period. It evaluates expiration in seconds as a delta from the item's last modified timestamp (_ts).
The system manages deletions automatically in the background using spare Request Units (RUs) for provisioned throughput accounts, ensuring you don't need to write custom cleanup scripts or manual sweep queries.

## transactional batch:
In Cosmos DB for NoSQL, grouping multiple point operations together is called a transactional batch.
You can combine document creates, reads, updates, and deletes into one transaction. All operations commit together, or all changes are rolled back if any operation fails. They must target the same container and the same partition key value. Microsoft Learn
For example, your orders container uses /customerId as its partition key:
Operation	Document ID	Partition key value
Create an order	ORD103	C101
Update an order’s status	ORD101	C101
Delete an order	ORD102	C101


These operations can share one transactional batch because every document belongs to customer C101’s logical partition.
Python example
Assume container is your connected orders container client, ORD101 and ORD102 already exist under C101, and ORD103 does not exist.
from azure.cosmos import exceptions

new_order = {
    "id": "ORD103",
    "customerId": "C101",
    "product": "Monitor",
    "quantity": 1,
    "status": "New"
}

batch_operations = [
    # Operation 1: Create
    ("create", (new_order,)),

    # Operation 2: Update selected fields
    ("patch", (
        "ORD101",
        [
            {
                "op": "set",
                "path": "/status",
                "value": "Shipped"
            }
        ]
    )),

    # Operation 3: Delete
    ("delete", ("ORD102",))
]

try:
    results = container.execute_item_batch(
        batch_operations=batch_operations,
        partition_key="C101"
    )

    print("All operations committed")

except exceptions.CosmosBatchOperationError as error:
    print(
        f"Operation {error.error_index + 1} failed. "
        "No changes from this batch were committed."
    )


The Python SDK accepts a list of operation tuples and executes them in the specified order. Microsoft Learn
What happens if the last operation fails?
Suppose ORD102 does not exist, so the delete fails:
Operation	Final result
Create ORD103	Rolled back; the new order is not saved
Update ORD101	Rolled back; its previous status remains
Delete ORD102	Fails because the document is missing

Types of indexes:
1. Range index
2. Composite index
3. Spatial index
4. Full text index
5. Vector index


Imagine your Cosmos DB container has 1 million product documents. You want products costing more than ₹500:
SELECT *
FROM c
WHERE c.price > 500

Without a usable index: Cosmos DB may need to read every document and check its price.
With a price index: Cosmos DB uses a separate lookup structure to locate matching documents. It then reads the documents needed for the result.
An index is like the index at the back of a book: you look up a topic and find its pages instead of reading the whole book.
Consider these four documents:
Document	Category	Price
P1	Electronics	500
P2	Electronics	900
P3	Furniture	700
P4	Electronics	300


1. Range index — look up values of a field
Think of the price index as this ordered lookup:
Price	Document
300	P4
500	P1
700	P3
900	P2


For WHERE c.price > 500, Cosmos DB can locate the entries 700 and 900, which identify P3 and P2.
A range index also helps with:
WHERE c.price = 500

ORDER BY c.price

You normally get these indexes automatically for string and number fields under the default indexing policy.

2. Composite index — look up a combination of fields
Suppose you want products sorted by category first, then price within each category:
SELECT *
FROM c
ORDER BY c.category ASC, c.price ASC

Think of the composite index as this combined lookup:
Category + price	Document
Electronics, 300	P4
Electronics, 500	P1
Electronics, 900	P2
Furniture, 700	P3


It keeps the combination in the order needed by your query.
Having separate indexes for category and price does not replace this combined index for a multiple-field ORDER BY. You must configure the matching composite index.


3. Spatial index — look up geographic locations
Imagine each store document contains its location.
Your question is:
“Which stores are within 5 kilometres of my location?”

A spatial index helps Cosmos DB find nearby locations efficiently. It is useful for stores, delivery vehicles, and location-based applications.

4. Full-text index — look up words in text
Imagine these descriptions:
P1: Wireless headphones
P2: Gaming monitor
P4: Wireless mouse

Your question is:
“Which descriptions contain the word wireless?”

A full-text index helps find P1 and P4 using text-search functions. It analyzes text into searchable terms. 

5. Vector index — look up similar meaning
Your search is:
“Headphones without cables”

The document says:
“Wireless headphones”

The wording differs, but the meaning is similar. An embedding model converts the text into numerical vectors, and a vector index helps find similar vectors. It does not understand the words directly. 

Remember the types by the question you are asking:
Your question									Index
Which products cost more than 500?				Range
Sort by category, then price					Composite
Which stores are nearby?						Spatial
Which descriptions contain “wireless”?			Full-text
Which descriptions mean something similar?		Vector

hierarchical partition:
A hierarchical partition key in Cosmos DB for NoSQL uses multiple fields in a defined order to partition documents.

Example:
| Order | company_id | customer_id |
|---|---|---|
| O1 | CompanyA | C101 |
| O2 | CompanyA | C101 |
| O3 | CompanyA | C102 |
| O4 | CompanyB | C101 |


regular partition on company_id

| Logical partition | Orders |
|---|---|
| CompanyA | O1, O2, O3 |
| CompanyB | O4 |


hierarchial partition on company_id and customer_id
then 
| Full partition-key value | Orders |
|---|---|
| `["CompanyA", "C101"]` | O1, O2 |
| `["CompanyA", "C102"]` | O3 |
| `["CompanyB", "C101"]` | O4 |

If we query
SELECT *
FROM c
WHERE c.company_id = "CompanyA"
  AND c.customer_id = "C101"

  it will go to one logical partition.
