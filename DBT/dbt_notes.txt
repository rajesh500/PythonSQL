DBT: data build tool:
DBT is a transformation tool used by data engineers and analytics engineers to convert raw data into clean, business-ready data using SQL.



# dbt Architecture:
Core Concept: dbt (data build tool) is an ELT transformation framework. It does not store data or run its own compute engine. Instead, it compiles modular SQL/Python code and pushes execution down to your cloud data platform.

1. The Five Architectural Layers

• Storage & Compute Layer (The Muscle): Your underlying data platform (Snowflake, BigQuery, Databricks, Redshift, DuckDB). It holds raw data and executes the SQL queries generated by dbt.
• Transformation Layer (The Brain): Organizes business logic into a three-tier modeling flow:
	• Staging (stg/): 1-to-1 with raw source tables. Handles column renaming, type casting, and basic cleaning.
	• Intermediate (int/): Optional layer for complex joins, filtering, and business logic before final aggregation.
	• Marts (marts/): Final fact and dimension tables (star schema) built for BI dashboards and end-users.
• Testing & Data Quality Layer: Runs automated assertions alongside transformations.
	• Generic Tests: Built-in YAML checks (unique, not_null, accepted_values, relationships).
	• Singular Tests: Custom SQL queries written to catch specific business logic errors.
• Lineage & Documentation Layer: Uses {{ source() }} and {{ ref() }} Jinja functions to automatically map dependencies into a DAG (Directed Acyclic Graph) and generate interactive documentation websites.
• Orchestration & Deployment Layer: Manages execution via CLI (dbt run, dbt test), dbt Cloud, or external orchestrators (Airflow, Dagster, Prefect) backed by Git version control.

Why use dbt instead of writing SQL directly?
You can write the same transformation directly in Snowflake. dbt becomes useful when you need to manage many related transformations reliably.
Need								How dbt helps
Organize SQL					Keeps transformations in a structured project
Run transformations in order	Tracks dependencies through ref()
Validate data					Tests uniqueness, missing values, relationships, and business rules
Understand data flow			Provides documentation and model lineage
Track changes					Works with Git for version history and code reviews
Avoid repeated logic			Supports reusable macros
Process growing datasets		Supports incremental models that process selected new or changed data
Deploy reliably					Supports automated execution and checks through CI/CD

sources in dbt:
A source in dbt is a declaration of an existing table or view that your dbt models read. You define it in a YAML file and reference it using source(). This lets dbt track where your data comes from, document it, and run data quality checks.


sources.yml / source.YAML
version: 2

sources:
  - name: ecommerce
    database: RAW_DB
    schema: ECOMMERCE

    tables:
      - name: customers
        description: Customer data loaded by ADF

        columns:
          - name: customer_id
            data_tests:
              - not_null
              - unique


select
    customer_id,
    trim(customer_name) as customer_name,
    lower(email) as email
from {{ source('ecommerce', 'customers') }}


what is it going to help is?
instead of hard coding table, defining in dynamic way. 



source freshness:
Source freshness in dbt checks whether your source data arrived recently enough. It helps detect ingestion delays before you build models using stale data.

Example:
 - name: EMP_TEST2
        description: Employee data loaded by ADF

        config:
          loaded_at_field: load_time
          freshness:
            warn_after:
              count: 1
              period: hour
            error_after:
              count: 2
              period: hour


seed:
Instead of manually creating small lookup tables like Country, Currency, Or Status in the database, we store them as csv files inside the seeds/  folder.
when we run dbt seed command, dbt automatically creates the table and load the data in snowflake.


ETL vs Seed
dbt seed puts static reference data inside Git, while ADF Copy Activity treats it as an unversioned external source.
dbt seed csv file can be tracked for change in the file, while ADF ETL pipeline doesn't have this option.


snapshot:
A snapshot in dbt preserves historical versions of records when source data changes. It implements Slowly Changing Dimension Type 2 (SCD Type 2).

two types of snapshots:
1. timestamp --> If the table is having timestamp fields, scd type 2 is completed based on these concepts (Refer, employee_snapshot.sql)
2. check --> If the table doesn't have any timestamp fields, scd type 2 is implemented based on main fields on the table (refer employee_check_snapshot.sql)


Jinja:
Jinja is a templating language used in dbt to generate SQL dynamically. It lets you use variables, conditions, loops, and reusable functions called macros. dbt renders the Jinja into SQL before the warehouse executes that SQL.


-- select '{{'Hello world'}}'

-- variable
{%set min_sal = 10000%}
{%set name = 'John' %}
select {{min_sal}}, '{{name}}'

-- if statement
{%if min_sal > 10000%}
select 'High Salary'
{%else%}
select 'Low Salary'
{%endif%}


{% set apply_salary_filter = true %}
select *
from SNOWFLAKE_DB.BATCHDEV.EMP_TEST2
{% if apply_salary_filter %}
where SALARY >= 1500
{% endif %}

-- for loop
{% set columns = ['ID', 'NAME', 'COUNTRY', 'SALARY'] %}
select 
{% for column in columns %}
        {{ column }}{% if not loop.last %},{% endif %}
    {% endfor %}
from SNOWFLAKE_DB.BATCHDEV.EMP_TEST2

# incremental model:
An incremental model in dbt builds a table once, then processes selected new or changed records on later runs. This can reduce processing time compared with rebuilding the entire table.


code:
{{
    config(
        materialized='incremental',
        incremental_strategy='merge',
        unique_key='ID'
    )
}}

select
    ID,
    NAME,
    COUNTRY,
    SALARY,
    LOAD_TIME
from SNOWFLAKE_DB.BATCHDEV.EMP_TEST2

{% if is_incremental() %}

where LOAD_TIME >= (
    select coalesce(
        max(LOAD_TIME),
        '1900-01-01'::timestamp_ntz
    )
    from {{ this }}
)

{% endif %}


is_incremental() --> checking is incremental or not
this --> query the target table and get the max timestamp.
where load_time >= 'max time stamp on target'.

# DBT Hooks
Hooks are SQL statements that dbt automatically executes before or after running a model, seed, or snapshot.

Prehook:
{{config(pre_hook = "delete from stg_employee")}}
select * from employee

Posthook:
{{config(post_hook = "insert into audit_log values (current_timestamp(), 'Employee', 'SUCCESS')" )}}
select * from employee

exposure:
In dbt, an exposure is a metadata resource that lets you document and track how your dbt models are used downstream in tools like BI dashboards, notebooks, or reports.
Exposures appear in your schema.yml alongside models, sources, and seeds, creating an explicit link between your data transformations and their consumers.
